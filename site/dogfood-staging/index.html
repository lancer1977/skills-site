# Dogfood Staging

The move from "V1 is stabilizing" to "this app is real" is a durable staging
deployment the owner actually lives in, not a demo. This skill sequences that
move and composes existing skills for the mechanics rather than duplicating
them — it does not replace `v1-delivery-shaping`, `mapped-frontier-development`,
`r620-deploy`/`stack-apply`, or `cloudflare-dns`; it's the checklist that
strings them together at this specific point in a project's life.

## When this applies

- The project already has a recorded V1 definition (`v1-delivery-shaping`) and
  is in or past stabilization — not still adding core feature scope.
- The goal is a **standing, durable** environment the owner dogfoods against
  repeatedly (days/weeks), not a one-off demo or a throwaway preview build.
- Distinct from the app's existing `dev.<app>.com` / `debug.<app>.com` /
  `localhost` tiers (per whatever ADRs the app already has — check
  `docs/decisions/` first): staging is the tier right before production,
  carries closer-to-real config, and is where the owner notices real gaps by
  actually using the thing.

If the project is still adding V1 scope, or doesn't have a recorded V1
definition yet, run `v1-delivery-shaping` first — dogfooding an undefined
scope just produces noise about missing features that were never promised.

## Phase 1 — Scope freeze

1. Confirm the V1 definition (or current stabilization scope) is current —
   re-read the owning epic, don't assume last session's understanding still
   holds.
2. Explicitly list what does **not** need to work yet for staging to be
   useful. Dogfooding surfaces real gaps fastest when the owner knows which
   gaps are already known-and-deferred versus genuinely new.
3. If standing up staging is itself a material change (new public hostname,
   new secret scope, new auth callback surface, a data-retention decision),
   run it through `mapped-frontier-development` Phase 0 rather than treating
   DNS + deploy as routine — this is exactly the "material deployment
   change" case that skill exists for.

## Phase 2 — Stand up the environment

1. **Naming**: `staging.<app-domain>` (e.g. `staging.channelcheevos.com`),
   distinct from any existing `dev.`/`debug.` tier. Confirm the actual domain
   the app uses — check existing ADRs/Infisical config before assuming
   `polyhydragames.com`/`polyhydra.app`; some apps (e.g. channel-cheevos) use
   their own domain.
2. **DNS**: use the `cloudflare-dns` skill — create the record before
   deploying, not after ("DNS first, not as an afterthought" is called out
   explicitly in `r620-deploy` because skipping it was real, avoidable
   friction previously).
3. **Deploy**: use `r620-deploy` for a first-time stack, `stack-apply` to
   reconcile an existing one. Staging must be a tracked Portainer/Swarm stack
   sourced from the repo's `homelab-gitops` definition — not a rogue local
   `docker run`/build (see the repo's own no-rogue-builds policy if it has
   one). Verify with the same rigor as production: real TLS cert subject,
   clean startup logs, a real endpoint through the public path — staging
   being "less important" than prod is not a reason to skip verification;
   it's the thing the owner is about to trust daily.
4. **Secrets**: staging gets its own credential set, never copied production
   secrets. Use `infisical-lookup` to find where sibling secrets for this app
   already live, `secret-apply` to generate/land new ones. Check whether the
   app has its own dogfood/staging secret-boundary ADR first (e.g.
   channel-cheevos's `docs/decisions/0001-auth0-dogfood-boundary.md` pattern
   — a real precedent for "staging must not become an implicit
   production/provider-migration change").
5. **Auth callbacks**: if the app has OIDC/OAuth login, staging needs its own
   callback/logout/origin allowlist entries (see `keycloak-admin` skill or
   the app's own auth provider config) — don't reuse production or dev
   callback URLs.

## Phase 3 — Dogfood tracking

1. Use the staging environment for real, ongoing use — not a single smoke
   test. The point is surfacing gaps only real use finds.
2. File every gap found as a GitHub issue on the app's repo, tagged so
   dogfood-sourced issues are distinguishable from originally-planned V1
   scope (e.g. a `dogfood` label). This keeps "what staging use taught us"
   separate from "what we already knew we'd build."
3. Triage using the same severity judgment as `v1-delivery-shaping`'s P0–P2
   language: repair blockers before graduation, defer polish to tracked
   follow-ups.
4. If the `quest-log` skill or a similar dashboard is already in use for this
   repo, surface dogfood-tagged issues there rather than starting a separate
   tracking document.

## Phase 4 — Graduation criteria

Staging is ready to inform a production cutover decision when:

- No open P0/P1 dogfood-tagged issues remain.
- The owner has used it continuously (not just tested it) for a length of
  time they're comfortable calling representative — this is a judgment call
  for the owner, not a fixed duration this skill should assume.
- Deployment mechanics (DNS, secrets, auth callbacks, verification steps
  above) are proven repeatable, not just "worked once."

Graduating to production is its own decision requiring its own explicit
confirmation — this skill stands up and validates staging; it does not
authorize a production cutover, merge, or DNS cutover to a production
hostname. Treat that as a separate, explicitly confirmed action per this
project's standing authorization rules for outward-facing changes.

## Related skills

- `v1-delivery-shaping` — defines the scope staging is meant to validate;
  run first if V1 isn't yet defined.
- `mapped-frontier-development` — Phase 0 packet for standing up staging when
  it's a material change, not routine.
- `cloudflare-dns`, `r620-deploy`, `stack-apply` — the actual DNS/deploy
  mechanics this skill sequences but doesn't duplicate.
- `infisical-lookup`, `secret-apply` — staging's own secret set.
- `keycloak-admin` — staging-specific OIDC callback config, if applicable.
- `quest-log` — surfacing dogfood-tagged issues if the repo already uses it.
